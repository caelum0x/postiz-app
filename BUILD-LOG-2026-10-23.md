# Build Log — 2026-10-23

## Round 1

### 1. Webhook delivery reliability (backlog item #6) — finished + fixed
Picked up an in-progress, uncommitted implementation and finished it to a working, verified state.

- `WebhookDelivery` Prisma model (additive migration): `webhookId`, `event`, `postId`, `url`, `requestBody`, `statusCode`, `success`, `attempts`, `error`, `durationMs`, indexed on `webhookId` and `(webhookId, createdAt)`.
- `Webhooks.secret` column (nullable, additive) — a per-webhook HMAC-SHA256 signing secret generated on create, exposed to the UI exactly once (at creation or regeneration), never again on list/read.
- `WebhooksService.sendWithRetry` — signs the payload (`X-Postiz-Signature: sha256=...`), retries up to 3 attempts with exponential backoff (500ms × 3^n) on 5xx/429/408, treats other 4xx as terminal, and always persists a `WebhookDelivery` row (success or failure) with status code, attempt count, error, and duration.
- `apps/orchestrator/src/activities/post.activity.ts`'s `sendWebhooks` now calls `sendWithRetry` instead of a raw unsigned `fetch` + silent catch.
- New endpoints on `webhooks.controller.ts`: `POST /webhooks/:id/secret` (regenerate), `GET /webhooks/:id/deliveries` (paginated log), `POST /webhooks/deliveries/:deliveryId/redeliver`. `/webhooks/send` (manual test-send) now also signs, dispatches through the existing SSRF-safe dispatcher, and returns a real status instead of swallowing errors.
- Frontend: `apps/frontend/src/components/webhooks/webhook.deliveries.tsx` (new) — paginated delivery log modal with status, attempts, error, and a redeliver action. `webhooks.tsx` wires a "Logs" column into the webhook list and a secret-reveal modal on create/regenerate.
- **Fix applied this round**: the "Regenerate secret" button existed as dead code (handler defined, never rendered) — wired it into the edit form, visible only when editing an existing webhook.
- Verified: `apps/backend`, `apps/orchestrator`, and `apps/frontend` all build clean (`nest build` / `next build`) with the new Prisma client generated.

### 3. Evergreen content recycling (backlog item #9) — built new, full depth
This was the biggest gap found this round: `/compare/socialbee` (shipped round 1) already **claims** "Postiz supports a recycle-after-days, category-based queue rotation for evergreen content" — but the feature didn't exist beyond an unused `EvergreenRecycle` Prisma model and a `RECYCLE` enum value some earlier session had added and never wired up. Built it for real so that comparison-page claim is true:

- `EvergreenRepository`/`EvergreenService` (new, mirrors the existing `PostEngagementRepository`/`Service` pattern) — create/list/pause/resume/remove a recycle schedule for an already-published post, plus a bounded (`BATCH_CAP = 25`) `runDueBatch()` that clones a due post's content/media/settings into a brand-new `Post` row (own id/group/Comments thread, `CreationMethod.RECYCLE`) through the exact same `validatePosts` → `mapTypeToPost` → `createPost` pipeline every other post-creation path uses — not a new, parallel content-writing path. A failed entry is pushed one interval out instead of retried immediately, and a recycle schedule whose original post was deleted deactivates itself instead of erroring forever.
- New daily Temporal workflow `evergreenRecycleWorkflow` (`apps/orchestrator/src/workflows/evergreen.recycle.workflow.ts` + `evergreen.activity.ts`), modeled on the existing `bestTimeToPostWorkflow` infinite-loop pattern, registered in `app.module.ts` / `workflows/index.ts` / `infinite.workflow.register.ts`.
- `POST|GET /posts/:id/evergreen` and `PUT|DELETE /posts/evergreen/:recycleId` on `posts.controller.ts`; only an already-`PUBLISHED` post can get a recycle schedule.
- Frontend: a new "Evergreen Recycling" calendar action (recycle-glyph icon, shown only on published posts) opening `evergreen.modal.tsx` — lists existing schedules with pause/resume/remove, and a form to add one (interval days + optional max recycles).
- Verified: `apps/backend`, `apps/orchestrator` (`nest build`) and `apps/frontend` (full production `next build`) all build clean with the already-generated Prisma client (schema/client were already in place from the earlier session; no schema change needed this round).

## Round 3

### 1. Internal approval workflow (backlog item #3) — built new, full depth
`Organization.requireApprovalForQueue` and `Post.pendingApproval` existed in the schema from an earlier session but had zero wiring (same shape of gap evergreen recycling and comment mentions were in before prior rounds). Wired it end to end:

- `Post.createdByUserId` (new, additive, nullable) + `User.createdPosts` back-relation — stamped on create from the WEB dashboard only, so an approver knows (and can be notified) who submitted a pending post. Every other creation path (API/MCP/autopost/bulk CSV/evergreen/clipping) never sets it, unaffected.
- `OrganizationRepository`/`OrganizationService`: `getApprovalForQueueSetting`/`updateApprovalForQueueSetting`/`requiresApprovalForQueue`. New `GET|POST /settings/approval-queue` (POST is ADMIN-gated), same shape as the existing shortlink-preference endpoints.
- `PostsService.createPost` now takes an optional `createdBy: { userId, role }` (WEB controller only). When the caller's role is `USER`, the save type is schedule/now, and the org has the setting on, the post is held as `DRAFT` with `pendingApproval: true` instead of going to `QUEUE` — `PostsRepository.createOrUpdatePost` grew the `createdByUserId`/`pendingApproval` params to do this at the DB layer. `PostsRepository.changeState` now always clears `pendingApproval`, since every path that calls it is an intentional final transition.
- `PostsService.approvePendingQueuePost`/`rejectPendingQueuePost` (+ `PUT /posts/:id/approve-queue`, `PUT /posts/:id/reject-queue`, ADMIN-gated) — approve reuses `changePostStatus` (the same path the internal "schedule" button and the public-preview `approvePublicPost` already use, so the real publish workflow actually starts); reject just clears the flag and leaves it a normal, editable draft. Both notify the original submitter via the existing `NotificationService.notifyUser`.
- `PostsService.getPendingApprovalPosts` + `GET /posts/pending-approval` (ADMIN-gated, declared before the generic `/:id` GET to avoid Nest route-matching ambiguity).
- Frontend: a yellow clock badge + inline Approve/Check and Reject/X glyph icons (no emoji) on the calendar card itself when `state === 'DRAFT' && post.pendingApproval`, visible only to ADMIN/SUPERADMIN viewers; a "Pending approval:" label replaces "Draft:" on the card. New `apps/frontend/src/components/settings/approval-queue-preference.component.tsx` (the toggle) and `pending-approvals.component.tsx` (the list with Approve/Reject buttons), both rendered in `teams.component.tsx` only for ADMIN+ roles. `manage.modal.tsx`'s save flow shows a distinct "Submitted for approval" toast instead of "Added/updated successfully" when the response indicates it.
- Verified: `apps/backend`, `apps/orchestrator` (`nest build`) and `apps/frontend` (full production `next build`, including route generation) all build clean with the newly generated Prisma client (`prisma validate` + `prisma generate` both clean).
